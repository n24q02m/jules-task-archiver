## 2024-07-18 - Restrict Content Security Policy
**Vulnerability:** The extension's Content Security Policy (CSP) in `manifest.json` lacked explicit `default-src 'none'` and broad network constraints, relying solely on script and object restrictions.
**Learning:** A permissive CSP allows unexpected resource loading and potential data exfiltration if an XSS vulnerability occurs. A strict whitelist (`default-src 'none'`) provides a robust defense-in-depth layer.
**Prevention:** Always define a strict CSP for extensions, setting `default-src 'none'` and explicitly allowing only required origins (e.g., `connect-src`).
## $(date +%Y-%m-%d) - Prevent Token Leakage via Fetch Redirects
**Vulnerability:** The custom `jFetch` wrapper in `background.js` attached sensitive `Authorization` headers (e.g., GitHub tokens) to requests but did not explicitly disable HTTP redirects. This left the extension vulnerable to token leakage if an initially trusted endpoint (like `api.github.com`) was compromised or misconfigured to return an open redirect to a malicious third-party server.
**Learning:** Modern `fetch` implementations generally strip `Authorization` headers on cross-origin redirects, but older environments or same-origin open redirects can still inadvertently forward credentials. In strict security contexts, especially when dealing with high-value tokens, explicit defense-in-depth is necessary.
**Prevention:** When writing network wrappers that transmit sensitive credentials, always configure `redirect: 'error'` or `redirect: 'manual'` in the fetch options. Failing securely and explicitly is preferable to silently trusting redirect chains.
